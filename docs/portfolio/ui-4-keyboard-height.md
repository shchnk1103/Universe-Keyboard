# PF-013 — UI-4 自定义键盘高度（含 UI-3 背景）

## 已决定（Human Product Owner，2026-10-22，Coordinator 会话）

- 先只做 UI-4（键盘高度）；UI-3（候选字大小）排在它之后。
- 最高行高：等模拟器实测之后再定。
- 没有完全访问时的行为：等一次真机验证之后再定。
- **硬要求：** 进入调节页面时，键盘不能被真正按动（不能输入、不能上屏）。这是预览方式的验收标准，不是方案选择。
- **预览方式：** 目前未定（App 内预览，还是在调节状态下用真正的键盘）；由 Spike 评估两种做法。
- **有效高度：** 接受“在宿主限制高度的场景里调高可能没有效果”；横屏等场景下键盘不能撑满整个屏幕、不能让用户看不清输入框里的内容，所以需要一条上限规则（具体取值待实测后由 Human 决定）。
- **步进：** 连续拖动，不做离散档位；保存时的精度待定。
- **验证方式：** 模拟器加真机；可用真机为一台 iPhone 13 Pro（iOS 27.0.1），只有这一种屏幕尺寸。
- **第一版的质量线：** 功能可用即可，不追求拖动过程的流畅度或视觉完美（参考的大厂键盘在拖动时也有外框滞后、松手后才重绘的卡顿）。

## 历史需求基线（来源 1，摘要）

- 目标：用户在主 App 里调整键盘高度。做法是**统一改变四行按键的行高**，不是缩放整个键盘；按键视觉尺寸、UIKit 约束与触控区域必须一致；不使用整体 `scaleEffect`。
- 参数：默认行高 45；最小 36（实验下限，需验证）；最大待定；步进待定；持久化的是用户期望的行高，不是宿主最终高度。
- 范围：26 键、九键、数字、符号、表情等适用页面；跨两行的特殊按键随约束同步变化。不改变：按键宽度、水平边距与间距、按键字号、候选栏高度、九键拼音路径栏高度、RIME 逻辑。
- 与 UI-1 / UI-2 的关系：必须基于已合并代码设计；路径行不参与行高调整，不得改变其 Sticky 状态机或造成重复展开 / 折叠、触控错位。来源 1 里的 256 / 290 与 254 / 288 只是不同阶段的估算，**不是最终高度合同**。
- 设置入口与交互：Universe Keyboard → 键盘布局 → 键盘高度；当前布局的实时预览，预览顶部竖向拖动手柄，重置 / 取消 / 确定；预览不执行真实输入；重置回 45 但不立即保存；确定后才保存；不提供宽度调整。
- 数据流：主 App 写入 App Group 共享设置，Keyboard Extension 在**下次键盘出现**时读取，不在输入中途重排。需要区分四个量：Preferred Row Height（用户保存）、Effective Row Height（环境实际允许）、Requested Keyboard Height（Extension 请求）、Host-Accepted Height（宿主接受）；宿主限制高度时可临时采用安全值，但不得覆盖已保存的期望值；配置无效 / 缺失 / 版本不兼容时回退默认。
- 完全访问：曾提出“无完全访问时入口可见但不可进入”，来源 1 自己写明**尚需验证**，不能直接作为实现约束。
- 需验证的项：26 键与九键一致性；数字 / 符号 / 表情页；九键跨行键；边缘键命中；最低行高下的误触与可访问性；候选栏与按键区不重叠；T9 Sticky Path 无回归；旋转与不同屏幕；扩展生命周期与重新呈现；主 App 与扩展共享配置；宿主高度约束；VoiceOver；取消 / 重置 / 异常恢复；Release 配置与真机。不得把模拟器请求成功等同于所有宿主接受该高度。
- 分阶段：Phase 1 Technical Spike（确认可行性、36 是否可用、最大安全行高、是否真需要完全访问、特殊键与 T9 Path 兼容）；Phase 2 实现（设置页、手柄预览、App Group 存储、扩展读取、有效高度限制与回退、测试与真机验收）。
- 第一版不做：自定义宽度、单独某行或底行高度、按键字号缩放、候选栏高度调节、T9 Path 高度调节、RIME 逻辑改动、跨进程实时强刷当前键盘。
- 与 UI-3 的关系：两者独立；UI-3 不改行高，UI-4 不改候选字号；都必须遵守 UI-1 / UI-2 的布局与触控合同。

## 参考：另一款 iOS 第三方键盘的调节界面（Human 提供的几张截图，2026-10-22，仓库外）

截图里看到的（只凭这几张图，不能推断它如何实现、数据存在哪里）：

- **入口**：容器 App 的“布局和显示”页里有一张“键盘高度调节”卡片，卡片里是一个带手柄的静态键盘缩略图和一个“设置”按钮；点“设置”进入调节页。
- **调节页**：真正的键盘显示在屏幕底部，上方是一个没有输入框的普通页面；键盘按键整体变暗；键盘顶部边缘、底部（空格键一带）、左右边缘各有一个拖动手柄；“重置 / 取消 / 确定”三个按钮叠在按键区中间；候选栏仍然显示；键盘下方是系统自己的地球键与麦克风栏。
- **范围**：调到最高时，键盘在竖屏上占了屏幕相当大的比例；调到最矮时明显矮于默认高度。这是对截图的粗略观察，不是测量。
- **拖动过程中**：键盘内部内容已经按新高度重新排布，而键盘外框仍停在原来的位置，松手之后外框才重绘，有一点卡顿。Human 的意见：第一版不追求改善这种效果。
- 我们第一版不做宽度调节和底部行单独高度（见历史需求基线的“不在第一版范围”），所以左右和底部的手柄不需要。

## 仓库盘点得到的相关事实（只读盘点，部分经 Coordinator 抽查；以 `docs/KEYBOARD_VALUES.md` 为准）

- 行高 `keyHeight` 目前是控制器实例上的不可变常量；高度请求与行约束的优先级都是 `defaultHigh`，可被系统压缩。
- 键盘只在 `viewDidLoad` 与有条件的 `viewDidAppear`（返回已有键盘时）刷新设置；布局在 `viewWillAppear` 里首次安装。“下次键盘出现时生效”与这个时序的真实关系待 Spike 确认。
- 主 App 没有检测完全访问的原语；仓库里没有任何实时键盘预览或“手柄”先例（最近的是引导页里的试打输入框与设置页里的静态缩略图）。
- `docs/PROJECT_CONTEXT.md` 描述的“216pt 时先隐藏再显示”机制，在代码里找不到；216pt 下的真实压缩结果 UNKNOWN。
- 两份布局测试把 254 / 288 / 45 / 46 写死，其中一份所在文件含 TD-020 记录的间歇性失败测试；`docs/TECH_DEBT.md` 的指引是不要再放宽超时。

## 待决问题与待验证假设（均未授权，Spike 的候选范围）

- 预览方式取哪一种，或两种都做 Spike 评估；预览与真实布局如何保持一致（App 里重新实现几何有漂移风险）；无论哪种，都必须满足“调节时不可输入”。
- 调节入口放在主 App 的设置页，还是放在键盘自己里面。若调节发生在键盘内部，偏好值也许可以存在扩展自己的存储里而不依赖共享容器，从而可能绕开完全访问的问题——这只是待 Spike 评估的假设。
- 上限规则：有效行高要同时受宿主允许的高度与一个“不遮挡输入内容”的比例限制；比例取值用 iPhone 13 Pro 的竖屏与横屏实测来定，由 Human 决定。
- 保存精度：连续拖动之后保存到什么精度。
- 拖动过程中何时向宿主请求新的键盘高度：随手实时请求，还是先只改内容、松手或确定时再请求（参考截图里是后者的样子，但无法确认）。
- 最高行高：模拟器实测各机型 / 方向下系统实际给到的高度，再定上限与步进。
- 完全访问：键盘没有完全访问时能否读取 App Group 里的共享设置；主 App 如何知道（目前没有检测原语）。
- 36pt 是否可用：行间距为 8 且触摸热区按相邻键中线补缝，推算内部行的有效命中高度约为行高加 8；这只是推算，需要实测和可访问性复核。
- 设置读取时机与首次布局安装的先后；是否会出现“先按默认高度画出来再跳变”。
- 在系统只给较低高度的宿主里“调高”可能看不出变化：产品上是否接受，是否需要在设置里提示。
- 对测试的影响：写死 254 / 288 / 45 / 46 的断言要改成读取默认值或参数化，且不能碰 TD-020 的失败模式。
